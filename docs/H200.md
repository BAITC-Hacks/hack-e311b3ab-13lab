# Диаризация на H200 через Teleport

Worker установлен отдельно в `~/qorytyn-diarization` на `mnvo-mv-01`.
Два GPU уже обслуживают другие задачи. Наш worker использует только GPU UUID
`GPU-7f76ca60-c049-6842-4ae4-5e4ba7a955d8` через `CUDA_VISIBLE_DEVICES`.
В проверенной H200-конфигурации PyTorch ограничен 10% памяти этого GPU. Другие процессы не останавливаются.

## Доступ к модели

Веса `pyannote/speaker-diarization-community-1` требуют принятия условий в
Hugging Face. Используется токен из стандартного хранилища Hugging Face на
сервере. Токен должен принадлежать аккаунту с доступом к модели; для fine-grained
токена необходимо разрешение на соответствующий gated repository.
Ключи Hugging Face, Teleport и пароль не помещаются в исходники.

## Запуск

Зависимости worker находятся в `services/diarization/requirements.txt`.
Перед первым запуском: Python 3.12, FFmpeg, CUDA-совместимый PyTorch,
`python3 -m venv .venv`, `.venv/bin/pip install -r requirements.txt`.
Рядом с `server.py` создаётся приватный `service.env` (права 0600):

```dotenv
DIARIZATION_TOKEN=<случайный-секрет>
CUDA_VISIBLE_DEVICES=GPU-7f76ca60-c049-6842-4ae4-5e4ba7a955d8
PYANNOTE_METRICS_ENABLED=0
HF_HUB_DISABLE_TELEMETRY=1
```

Запуск worker: `sh start.sh`. Адрес только `127.0.0.1:18765`.
Для фонового запуска использовать `nohup sh start.sh > service.log 2>&1 &`.
Не запускайте второй worker на том же порту.

На Mac из каталога проекта: `sh scripts/gpu-tunnel.sh`.
Сессия Teleport должна быть действительна. Туннель работает, пока эта команда
запущена. По истечении сертификата пользователь повторяет `tsh login`.

`GET http://127.0.0.1:18765/health` должен вернуть `ready: true` и NVIDIA H200.
После этого в локальном `.env` установить:

```dotenv
DIARIZATION_URL=http://127.0.0.1:18765
DIARIZATION_TOKEN=<тот-же-секрет>
```

Перезапустить веб-приложение только после завершения текущих обработок.
Для отключения GPU очистить `DIARIZATION_URL` и перезапустить приложение.
Старые протоколы не переписываются; для проверки загрузить новую запись.

## Локальный backend и Docker

Для backend, запущенного на Mac через uvicorn, используйте `http://127.0.0.1:18765`.
В Docker `127.0.0.1` указывает на сам контейнер, а не на Mac. На Docker Desktop
используйте `http://host.docker.internal:18765` и проверьте доступ из backend:

```bash
docker compose exec backend python -c "import urllib.request; print(urllib.request.urlopen('http://host.docker.internal:18765/health').read().decode())"
```

Если loopback-туннель недоступен из Docker, оставьте worker закрытым и запускайте
backend локально с этим туннелем, либо организуйте туннель внутри приватной сети
контейнера. Не открывайте порт worker в публичную сеть ради подключения Docker.
После изменения `.env`: `docker compose up -d --force-recreate backend`.
Проверка Docker-пути зависит от сетевой конфигурации хоста; `diarization_configured`
в `/api/health` означает наличие настройки, а не доступность GPU.

## Контракт и ограничения

`POST /diarize`: Bearer-токен, multipart `file`, необязательный `num_speakers`.
Ответ: `turns[{start,end,speaker_id}]`, `duration_seconds`, `model`, `gpu`,
`elapsed_seconds`. Один запрос одновременно. Лимит 100 МБ и 10 минут.
Файлы удаляются после запроса. До готовности модели возвращается 503,
при занятости — 429, повреждённом аудио — 400.

Речь распознаётся через разрешённый Tilqazyna. Worker определяет только
акустические метки, а не имена. Метки объединяются с исходными timestamps слов;
неоднозначные пересечения остаются неизвестными. Имена назначает пользователь.

При ошибке GPU обработка завершается с понятной ошибкой. Повтор использует
сохранённый ASR; ошибки нельзя маскировать вымышленными метками говорящих.
Для старых сохранённых сегментов без слов остаётся менее точная привязка по
интервалам сегментов. Новые записи используют слова.

## Остановка

Остановить только процесс нашего worker и наш локальный туннель. Не выключать
сервер, GPU или существующие ASR/LLM/TTS-сервисы: машина общая.
