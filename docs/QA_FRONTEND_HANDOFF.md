# Q&A и интеграции: передача frontend

Текущий Q&A — демонстрация, без API, поиска по протоколам, OAuth и отправки пользовательских вопросов внешним сервисам.

## Компоненты

- `frontend/src/features/qa/MeetingQA.tsx` — единый чат на лендинге и во вкладке совещания. История, готовые вопросы, ввод, ошибка, сброс, раскрывающиеся цитаты.
- `frontend/src/features/qa/demo.ts` — типы `QAClient`, `QAAnswer`, `QASource` и вымышленные данные. Произвольный вопрос получает сообщение об ограничениях демо.
- `frontend/src/components/Integrations.tsx` — карточки источников. Аудиофайл доступен; Zoom, Microsoft Teams, Google Meet и календарь помечены «Скоро». Нажатие раскрывает описание, аккаунты не подключаются.

## Подключение реального Q&A

1. Реализовать `QAClient.ask(question, signal)` на основе защищённого API. Привязать клиент к meeting ID в рабочем экране; не использовать реальные данные на публичном лендинге.
2. API должен проверять права на чтение этого совещания, возвращать текст и существующие источники. Расширить QASource идентификатором сегмента и временем в секундах для перехода к аудио.
3. Передать клиент в MeetingQA. Сейчас подписи в компоненте намеренно всегда говорят «демо»: при реальном подключении добавить явный режим live/demo и изменить подписи только для live.
4. Для live передавать подсказки вопросов отдельно от demoQuestions. Не применять готовые ответы к реальным встречам.
5. Сохранить AbortSignal, обработку ошибки и повтор. Добавить тесты прав, отсутствия источника, таймаута и смены meeting ID. Публичный лендинг должен продолжать использовать demoQAClient.

Визуальный референс: https://meeting.ai/en — цепочка источников/результатов, примеры запросов и FAQ. Макет, тексты, иллюстрация и палитра HATTAMA собственные; чужие показатели аудитории, тарифы и заявления о безопасности не перенесены.
